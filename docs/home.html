SpeedCE 的名字取自 Speed（速度）与 CE（Connectivity & Experience，连通性与体验）的缩写寓意——帮助用户在几秒钟内掌握目标网站或 IP 在不同地区的访问速度与连通状态。

与传统「只给一个总分数」的测速工具不同，SpeedCE 的核心理念是：

让每一次检测，都能在一幅地图上被看见。

当你输入一个域名或 IP 并点击「开始测速」后，SpeedCE 会从分布在中国各省、各运营商线路，以及全球多个国家和地区的检测节点，向你的目标发起 HTTP、HTTPS、PING、TCPing、DNS 或路由追踪检测。检测结果不会淹没在冗长的表格里，而是同步呈现在交互式地图上：绿色代表通畅，红色代表异常，动态标记告诉你哪些节点正在检测、哪些还在排队。DNS 查询还会汇总各节点解析一致性；路由追踪则展示逐跳路径，并支持 MTR 模式查看丢包与延迟统计。

对于中国用户而言，这意味着你可以一眼看出：是广东电信慢，还是新疆联通不通；是国内整体正常、海外异常，还是三网全面超时。对于面向全球业务的站长，你还可以切换「全球节点」范围，观察欧美、东南亚、中东等地区的访问质量差异。

二、核心功能详解

2.1 六种检测工具：下拉菜单一键切换

不同的问题，需要不同的检测方式。SpeedCE 在测速表单顶部提供工具下拉菜单，可在同一页面切换六种检测模式，无需跳转其他页面。

工具 说明
HTTP 80 端口 Web 服务可用性与响应速度
HTTPS 443 端口加密 Web 服务（含 SSL/TLS 握手）
PING ICMP 连通性与网络延迟
TCPing 指定 TCP 端口连通性（适用于禁 Ping 的服务器）
DNS 从各节点查询 DNS 记录（仅支持域名）
路由追踪 从所选单节点对目标进行 Traceroute，可选 MTR 模式

HTTP 测速

适用于检测网站在 80 端口的 Web 服务可用性与响应速度。当你想知道「这个域名能不能被正常访问」「页面返回是否及时」时，HTTP 模式是最直接的选择。

典型场景：

  • 新站上线后验证 Web 服务是否正常；
  • 排查 Nginx / Apache 配置是否生效；
  • 检测 CDN 回源是否成功；
  • 确认 HTTP 强制跳转 HTTPS 之前的中间状态。

HTTPS 测速

适用于检测 443 端口的加密 Web 服务。相比 HTTP，HTTPS 测速会包含 SSL/TLS 握手过程，因此能更真实地反映用户通过浏览器访问你网站时的体验。

典型场景：

  • 证书部署后验证全站 HTTPS 是否可用；
  • 排查 SSL 配置错误导致的部分地区访问失败；
  • 评估 HTTPS 对首屏时间的影响；
  • 电商、支付、登录页等安全页面的可用性巡检。

PING 测速

适用于检测目标 IP 的 ICMP 连通性与网络延迟。PING 不关心 Web 服务是否配置正确，只回答一个问题：这个 IP 从远方能不能「打得通」，延迟是多少毫秒。

典型场景：

  • 购买 VPS 后验证商家宣传的线路质量；
  • 服务器禁 Ping 前的备用方案（可配合 HTTP 模式）；
  • 快速判断是网络层问题还是应用层问题；
  • 对裸 IP、非 Web 服务进行基础连通性测试。

TCPing 测速

适用于检测目标 指定 TCP 端口是否可达。当服务器禁用 ICMP（Ping 不通）时，TCPing 是验证「端口是否开放、服务是否在监听」的实用替代方案。选择 TCPing 后，可自定义端口号（如 22、80、443、3389 等）。

典型场景：

  • 云服务器禁 Ping，但需确认 443 端口是否开放；
  • 排查 SSH（22）、RDP（3389）、数据库等非 Web 端口连通性；
  • 验证防火墙规则是否误拦特定端口。

DNS 查询

适用于从各检测节点分别查询域名的 DNS 记录，支持 A、AAAA、CNAME、MX、TXT、NS 等记录类型。仅支持域名输入（不支持直接输入 IP）。结果除地图展示外，还提供专用详情面板：各节点解析值、TTL、耗时，以及解析一致性统计（是否所有节点返回相同结果）。

典型场景：

  • 改 DNS 后验证全国/全球解析是否已生效；
  • 排查 DNS 污染、解析不一致、CDN 切量异常；
  • 检查 MX、TXT 等邮件与验证记录是否正确传播。

路由追踪（Traceroute / MTR）

适用于查看从某一选定节点到目标的逐跳路由路径。与 HTTP/PING 等多节点并发检测不同，路由追踪需先选择探测节点，再从该节点发起追踪。支持普通 Traceroute 与 MTR 模式（显示每跳丢包率、最近/平均/最佳/最差延迟等统计）。

典型场景：

  • 定位跨境、跨省访问慢在哪一跳；
  • 排查路由绕行、中间节点超时；
  • 对比电信/联通/移动从不同省份出发的路径差异。

六种工具互补，构成完整的「DNS → 网络层 → 传输层 → 应用层」检测链路。 例如：DNS 解析正常但 HTTPS 失败，问题可能在 Web 服务或证书；PING 不通但 TCPing 443 成功，说明 ICMP 被禁但服务正常；全国 HTTPS 正常但某省慢，可用路由追踪定位瓶颈跳。

三、谁应该使用 SpeedCE？

3.1 个人站长与博客作者

你一个人维护网站，没有 7×24 监控预算，但希望在改完 DNS、换完主题、迁完服务器后，能快速确认「全国各地还能不能打开」。

推荐用法：

  1. 改 DNS 后，用 HTTPS 模式测主域名，范围选「中国节点」；
  2. 看地图有没有大片红色，重点看目标用户所在的省份；
  3. 若有海外读者，再切「全球节点」补测一遍。

3.2 VPS / 云服务器玩家

在 HostLoc、NodeLoc 等社区里，「线路好不好」是永恒话题。商家宣传 CN2 GIA、9929、CMIN2，买家将信将疑。

推荐用法：

  1. 拿到 VPS IP 后，用 PING 模式 + 中国节点，看电信/联通/移动延迟分布；
  2. 若 PING 不通（部分云厂商禁 ICMP），改用 HTTPS 模式测 80/443；
  3. 截图地图发帖，比一句「我本地 ping 20ms」更有说服力。

3.3 企业运维与 SRE

你们有监控系统，但业务同学、合作方、客户经常问：「为什么我这里慢？」你需要一个对外可分享、结果直观的第三方测速链接。

推荐用法：

  1. 故障期间，把 SpeedCE 测速结果截图附在工单回复里；
  2. 新服务上线前，建立「中国 + 全球」基线数据；
  3. 与 CDN 厂商扯皮时，用多省份数据说话。

3.4 前端与全栈开发者

你在做国际化站点，需要验证静态资源 CDN、API 网关、Serverless 函数在不同区域的响应。

推荐用法：

  1. 分别测 www.example.com 与 api.example.com；
  2. HTTP vs HTTPS 对比，排查证书或混合内容问题；
  3. DNS 模式查 A/AAAA 记录，确认 CDN 切量是否全球一致；
  4. 全球节点模式下，关注欧美与东南亚差异，指导边缘节点部署。

3.5 跨境电商与外贸团队

客户说「网站打不开」，你怀疑是 GFW、DNS 污染还是服务器宕机。

推荐用法：

  1. 先用 HTTPS 测国内节点，确认源站是否存活；
  2. 再用全球节点测客户所在国（如美国、德国、阿联酋）；
  3. DNS 模式检查域名在海外是否解析到正确 IP；
  4. 若国内正常、海外异常，重点查 CDN 与跨境线路；若国内也异常，先修源站。

七、技术视角：六种检测工具的原理与局限

7.1 PING（ICMP）测速

PING 使用 ICMP 协议，测量数据包往返时间（RTT）。优点是简单、快速；缺点是：

  • 部分服务器禁用 ICMP，会显示超时，但 Web 服务仍正常；
  • PING 只反映网络层，不能代表页面加载速度；
  • 高延迟不一定等于「网站慢」，低延迟也不一定等于「网站快」。

结论： PING 适合排查「路通不通」，不适合单独评价「网站快不快」。

7.2 HTTP / HTTPS 测速

HTTP(S) 测速模拟用户发起 Web 请求，测量从发起连接到收到响应的时间。HTTPS 还包含 TLS 握手，更接近真实浏览器访问。

优点是更贴近实际业务；缺点是：

  • 受服务器并发、WAF、CDN 缓存策略影响；
  • 单次测速不代表长期趋势，建议多次对比；
  • 动态页面与静态页面差异大，测速结果需结合页面类型解读。

结论： 网站可用性检测，优先 HTTPS；IP 连通性初筛，用 PING；禁 Ping 时用 TCPing。

7.3 TCPing 测速

TCPing 向目标 IP 的指定端口发起 TCP 连接（三次握手），测量连接建立时间。不依赖 ICMP，因此适用于禁用 Ping 的云服务器。

优点是能验证端口级可达性；缺点是：

  • 只能反映指定端口，不能代表所有服务；
  • 部分防火墙会丢弃 TCP SYN 包，结果可能显示失败但 UDP/其他协议正常；
  • 需正确填写端口号（HTTP 80、HTTPS 443、SSH 22 等）。

结论： 服务器禁 Ping 时，用 TCPing 替代 PING 做连通性初筛。

7.4 DNS 查询

DNS 模式从各检测节点向配置的递归 DNS 发起查询，返回记录值、TTL 与查询耗时。支持 A、AAAA、CNAME、MX、TXT、NS 等类型。

优点是能发现解析不一致、污染与传播延迟；缺点是：

  • 仅支持域名，不支持直接输入 IP；
  • 各节点使用的 DNS 递归服务器可能不同，结果差异需结合上下文解读；
  • 单次查询不代表长期解析稳定性。

结论： 改 DNS、上 CDN、排查「部分地区打不开」时，优先用 DNS 模式做全国/全球交叉验证。

7.5 路由追踪（Traceroute / MTR）

路由追踪从单个选定节点向目标发送逐跳探测包，记录每一跳的 IP 与往返延迟。MTR 模式在 Traceroute 基础上持续探测，统计丢包率与延迟分布。

优点是能定位网络路径瓶颈；缺点是：

  • 每次仅从一个节点出发，需手动切换节点对比不同路径；
  • 中间节点可能不响应探测包，显示为 * 或超时；
  • 跨境路由可能因政策或运营商策略出现绕行，结果会随时间变化。

结论： 当「通但慢」或「只有某省/某国慢」时，用路由追踪定位问题跳。

7.6 多节点测速的意义

中国互联网呈「分省分网」结构，同一网站在不同省份、不同运营商的体验可能天差地别。全球互联网则受跨境路由、国际出口带宽、当地 ISP 质量影响。

因此，单点测速必然有偏见，多节点测速才是公平视角。 SpeedCE 的价值，正是用分布式的节点网络，帮你还原这种「分布式真实」。

不可以。私有地址和保留地址会被拦截，这是为了防止滥用。

为保障服务稳定，平台对过高频率的请求会进行限流提示（「请求过于频繁，请稍后再试」）。正常使用不会受影响。

部分节点可能因临时繁忙、网络不可达或调度策略被跳过，属于正常现象。关注整体通畅率即可。

Q7：和 PageSpeed Insights、GTmetrix 有什么区别？

PageSpeed、GTmetrix 侧重页面性能评分、Core Web Vitals、前端优化建议；SpeedCE 侧重多地区网络连通性与延迟。两者互补：一个回答「页面优化得好不好」，一个回答「各地用户能不能访问、快不快」。
